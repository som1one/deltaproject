# Остаточные вилки ТЗ и план тестирования

Документ фиксирует:
- что еще нужно дожать до полного соответствия ТЗ;
- что именно тестируем сейчас (MVP + админка) и какой ожидаемый результат.

## 1) Остаточные вилки по ТЗ

### Вилка A: Referral username flow
Статус: **не закрыто до конца**.

Сейчас:
- `GET /referral/{username}` работает через fallback по `link` (contains).
- отдельного поля `username` в модели `ReferralLink` нет.

Нужно решить и зафиксировать:
- добавляем ли `username` как отдельное поле в БД (`unique + index`);
- делаем ли `GET /referral/{username}` основным production-flow для регистрации.

См. детали: `backend/REFERRAL_USERNAME_FLOW.md`.

### Вилка B: Админ-финсхемы блогеров
Статус: **в БД и сервисе есть, админ API нет**.

Сейчас:
- таблица `blogger_finance_schemes` есть;
- сервис распределения денег есть.

Нужно решить:
- добавляем ли обязательный блок админ-ручек:
  - `GET /admin/finance-schemes`
  - `GET /admin/finance-schemes/{blogger_id}`
  - `PUT /admin/finance-schemes/{blogger_id}`

### Вилка C: Единая политика auth-кодов для админки
Статус: **частично согласовано**.

Сейчас:
- без токена -> `401`;
- токен не-админа -> `403` (через `get_current_admin`).

Нужно финально зафиксировать:
- оставляем стандартную схему `401/403`, или
- принудительно приводим все неуспехи админ-авторизации к `401` по ТЗ.

### Вилка D: Автотесты критических денег
Статус: **ручной прогон есть, автотестов мало**.

Нужно решить объем before-prod:
- минимальный набор интеграционных тестов по финансам и идемпотентности;
- или переносим это на следующий этап.

## 2) Что тестируем сейчас и что должно быть

### 2.1 Smoke/infra
- Тест: `GET /health`
- Ожидаем: `200`, `{"status":"ok"}`.

- Тест: миграции `alembic upgrade head`
- Ожидаем: успешный апгрейд до последней ревизии без ручных правок.

### 2.2 Auth
- Тест: `POST /auth/login` c данными админа
- Ожидаем: `200`, возвращаются `token` и `refresh_token`.

- Тест: `POST /auth/login` с пользователем Worker/Bloger
- Ожидаем: `403`.

- Тест: `POST /auth/user-login` c Worker/Bloger
- Ожидаем: `200`.

- Тест: `POST /auth/user-login` c Admin
- Ожидаем: `403`.

- Тест: деактивированный пользователь пытается логиниться
- Ожидаем: `401`.

### 2.3 Кабинет пользователя (me)
- Тест: `GET /me`
- Ожидаем: профиль + `balance_pending_confirmation_kopeks`.

- Тест: `GET /me/deals`
- Ожидаем: список сделок пользователя (`DealRead[]`), без чужих сделок.

- Тест: `GET /me/ledger`
- Ожидаем: только записи текущего пользователя, корректная пагинация.

- Тест: `POST /me/payout-requests`
- Ожидаем: создается запись со статусом `payout_request`, при нехватке средств -> `400`.

### 2.4 Сделки (worker/bloger)
- Тест: `POST /deals` от Worker
- Ожидаем: `200`, создается сделка со статусом `NEW`.

- Тест: линейные переходы статуса `NEW -> REVIEW -> CONFIRMED -> PAID -> COMPLETED`
- Ожидаем: валидные переходы проходят, невалидные -> `400`.

- Тест: переход в `PAID` повторно
- Ожидаем: не создаются дубли начислений (идемпотентность по `idempotency_key`).

### 2.5 Админ: пользователи и роли
- Тест: `GET /admin/users` с фильтрами `role/email/linked_to`
- Ожидаем: корректный отфильтрованный список + `total`.

- Тест: `PATCH /admin/users/{user_id}` для `role/percent/is_active`
- Ожидаем: поля обновляются, конфликтные кейсы -> `409`.

- Тест: `GET /admin/users/{user_id}/ledger`
- Ожидаем: аудит только выбранного пользователя.

- Тест: `DELETE /admin/users/{user_id}`
- Ожидаем: `204`, но удаление текущего/единственного админа -> `409`.

### 2.6 Админ: сделки
- Тест: `GET /admin/deals` с фильтрами `status/worker_id/bloger_id/from/to`
- Ожидаем: релевантные сделки; при запросе несуществующего worker/bloger фильтра -> `404`.

- Тест: `PATCH /admin/deals/{deal_id}/status` с `reason`
- Ожидаем: статус меняется, причина сохраняется в `deal_admin_logs`.

- Тест: `POST /admin/deals/{deal_id}/recalc-finance` с `reason`
- Ожидаем: идемпотентный пересчет, без дублей проводок.

### 2.7 Админ: выплаты и журнал
- Тест: `GET /admin/ledger` с фильтрами `status/user_id/from/to/limit/offset`
- Ожидаем: корректная выборка и пагинация.

- Тест: `GET /admin/ledger/{entry_id}`
- Ожидаем: детали операции, `404` если не найдена.

- Тест: `POST /admin/payouts/{entry_id}/complete`
- Ожидаем: статус становится `completed`, баланс пользователя уменьшается; конфликты -> `409`.

## 3) Критерий приемки бэка (MVP)
- Все перечисленные smoke и функциональные тесты проходят.
- Нет дублей финансовых проводок при повторных вызовах критичных endpoints.
- Админ-маршруты закрыты ролью `Admin`.
- Все денежные поля и расчеты работают в копейках (`int`).
- Документация API синхронизирована с фактическим поведением.
